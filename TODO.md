  - Survey 2026-11-21 (Fedora 45 VMs, bench KW2/KW6/KW7, not in the suite): the app sent the right keys for all 26 accents, but no app made the character. Konsole and ptyxis got ^U, the hex and Enter. A GTK4 text box (Plasma and GNOME) and a Qt6 text box (Plasma) got the hex digits as text ("00e9"). Plasma runs no IBus or fcitx, so nothing there handles Ctrl+Shift+U (its input method is plasma-keyboard, see the follow-up). GNOME runs IBus and still failed; 10x slower timing did not help.   - GNOME fix through setup (owner, 2026-11-21), no root: `--setup --install` run as the user writes `IBUS_ENABLE_CTRL_SHIFT_U=1` to `~/.config/environment.d/90-gamepad-osk.conf` (applies at next login; not tested yet) and prints what it changed and how to undo it (delete the file). - [ ] KDE Alt+Tab: in a Plasma VM, a quick second Alt+Tab or the next d-pad move comes 0.3-1.5 s late. Cause: input, key sending and drawing share one thread, and SDL_RenderPresent waits on KWin after Alt+Tab. Mostly late, not lost (one run landed on the wrong key). VM draws in software, so try it on real KDE hardware first. Fix is the input thread split below.
- [ ] KDE Alt+Tab, keyboard not visible: in the Plasma VM, while the KWin window switcher is open, KWin does not show the keyboard. It comes back when Alt is released (3 s timeout or the next key). The app does not hide itself (Alt stays held, no hide). Check on real KDE hardware with the item above. Cause (KWin source): an unknown layer-shell namespace (ours is "gamepad-osk") makes KWin treat the keyboard as a normal window, and the highlight effect fades normal windows to 0 while the switcher is open. A test build with namespace "on-screen-display" stayed visible. Plan: if real KDE shows it too, file a KDE bug first; rename only if that is slow and users complain (the rename breaks user rules that match "gamepad-osk", for example Hyprland layerrule).
